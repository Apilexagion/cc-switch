# 148 版复杂会话续聊修复

## 版本与问题范围

修复基于 `v4.0.42-codex-auth-148`（提交 `673fc16a51c2685012f226d572de602bf237b551`），提交分支为 `nux-cc-switch-unlock-turn-limit`。PR 以保留 148 版续接实现的 `codex/pr2-stream-error-preservation-ci` 为基线，仅审阅本次续接修复。远程 `feat/magpie-inspired` 后续已撤回旧版续接功能，因此本 PR 不直接以该分支或 `main` 为目标。

原实现遇到明确的会话轮次上限后更换身份、归档普通模型及工具历史，但始终保留原生 `reasoning`。归档代码已有推理完整归档能力，却只在测试中启用。如果上游仍依据原生推理历史判断轮数，普通归档后的唯一一次重试仍可能到限。既有真实报错证明续接后再次到限；上游计数实现不可见，不能据此声称已确认其内部具体计数算法。

## 修复行为

1. 首次明确到限时，保持原有行为：更换上游身份，保留原生推理，按开关完整归档普通历史并重试。
2. 只有该请求再次明确到限、启用了完整历史归档、正文仍含原生推理且尚未升级时，才增加一次兼容重试：再次更换身份，将完整推理 JSON 写入本机内容寻址归档；出站文字历史保留可读摘要及 SHA-256 校验引用，避免不透明密文膨胀模型上下文。
3. 兼容模式按供应商和客户端聊天保存在现有进程内会话映射中。后续请求沿用，正常轮换及迟到的并发失败不能降级该模式。
4. 同一客户端请求、同一供应商最多两次额外尝试。没有原生推理、未开启归档或已经在兼容模式时，最多一次额外尝试。普通 400、鉴权、配额、上下文超长和流输出后的错误不因此增加重试。
5. 只有重试正常完成后才显示成功通知。兼容续接成功会补充说明：历史推理数据已完整归档，不再复用原生推理状态。

用户、系统、开发者消息及工具定义维持原生；普通历史和推理的数据完整保存，不生成摘要、不执行工具、不调用 `/compact`。媒体、动态工具注册及其配对调用、原生压缩条目、顶层引用沿用既有保留规则。未知协议仍停止，不生成部分归档。

同时修复子代理密文消息的传递边界：`agent_message` 如果包含原生密文，普通和兼容模式均原样保留，避免把任务正文转成接收方不能解读的密文字符串。含密文不豁免未知兄弟内容块的校验；没有密文或媒体的普通子代理文字仍可归档。

## 兼容边界

“密文完整保存”不表示模型仍能像原生推理协议一样复用该状态；兼容模式明确改变了它的协议语义。媒体或其他必须原生保留的内容、上游引用、额度和上下文窗口仍可能导致拒绝，本修复不承诺所有上游无限续聊。映射仍采用原有内存生命周期，重启或过期后会重新判断。

## 验证方式

以下命令均在仓库根目录执行，只使用本机模拟上游，不读取真实供应商密钥或修改运行配置：

```powershell
cargo test --manifest-path src-tauri/Cargo.toml --lib session_identity --locked --offline
cargo test --manifest-path src-tauri/Cargo.toml --lib codex_history_archive --locked --offline
cargo check --manifest-path src-tauri/Cargo.toml --lib --locked --offline
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
git diff --check
```

回归用例覆盖 129 条原生推理、两阶段重试及停止预算、跨回合复用、无关错误、无原生推理、完整 JSON 恢复、媒体及工具注册保留，以及 16 个并发升级共享同一身份代。

真实中转站是否已覆盖原失败场景，仍需使用本修复编译的程序复测；模拟测试通过不等于已完成真实 200 轮验证。

## 本机验证结果

- 会话身份及转发相关测试：63 项通过，0 项失败。
- 历史归档相关测试：19 项通过，0 项失败，包含子代理密文原生保留和未知内容校验。
- 非测试配置的 Rust 库编译检查通过。
- Rust 格式检查、差异空白检查及所有界面语言 JSON 解析通过。
- 后续实测已构建并运行临时修复版，开启当前供应商的脱敏诊断，修改前已备份数据库；未覆盖原安装目录，未重新完成真实中转站 200 轮测试。

## 原审计聊天恢复实测

2026年11月27日实测：原审计聊天先触发普通轮换，仍明确到限后触发 reasoning_archive_retry，将129条原生推理转为归档并取得上游成功响应。首次验证随后因客户端上下文窗口不足中断，因此不能仅凭HTTP 200或成功通知宣称整轮恢复。

随后构建了本机推理存储版本，避免将不透明密文直接作为长文本发送。原聊天在验证B中发生了客户端 contextCompaction，之后正常回复“原会话恢复验证-B”；验证C实际执行只读命令并返回 version=4.0.42 和分支 fix/148-session-history-recovery，最终回复包含“原会话工具恢复验证-C”。

结论：原聊天已经恢复普通回复和工具往返。但该恢复经过客户端上下文压缩，不能证明完整历史不压缩续聊成功，也不构成200轮验证通过。存储版本的本机回归通过，不等于原失败聊天无压缩恢复已得到验证。

完整工具读取证据保存于仓库上级 audit-results/live-recovery/原聊天恢复验证.json。密文归档目录采用应用配置目录下的 codex-reasoning-archive，文件按内容哈希命名，原文落盘并读回校验；引用不能供模型解密或还原原生推理状态。
